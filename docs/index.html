Prioritizing Content Refresh Opportunities Using Historical Search Signals

This project looks at a simple practical problem: if a content team has a large number of pages, which ones should they review first?

Abstract

The aim of this project was to test whether historical search and content signals could be used to rank pages that may deserve refresh attention. I used page-level search performance data from the FlyRank ML Internship warehouse and built a simple baseline, a Logistic Regression model, and a Random Forest model. To make the evaluation more realistic, I split the data by client instead of randomly splitting individual rows. On the final grouped test set, the Random Forest reached a Precision@20 of 0.95 and a Precision@50 of 0.96. The result suggests that these signals can be useful for prioritizing manual review, but the model should not be treated as proof that refreshing a page will directly improve its search performance.

Introduction / Problem Statement

A content team may have hundreds or thousands of pages, and reviewing all of them manually is not practical. The useful question is therefore not just "which pages are declining?" but "which pages should be checked first?"

My goal was to build a ranking system that could help answer that question. Instead of making an automatic decision to rewrite or refresh a page, the model produces a review queue that a person can inspect.

Data

I used the FlyRank ML Internship warehouse release through Hugging Face. The raw search-performance data was aggregated to the content-page level using DuckDB.

For the final version of the model, I only used information available before the June 2026 outcome period. The target was whether June impressions were lower than May impressions.

I also filtered out pages with fewer than 50 May impressions. During testing, very low-volume pages created misleadingly strong model results because a change from one impression to zero was technically counted as a decline. The minimum visibility threshold helped make the final ranking more useful in practice.

Public results do not include client names, domains, URLs, private queries, credentials, or raw data exports.

Methodology

The final model used a small set of historical features:

  • Content age
  • 90-day impressions
  • Average search position
  • Click-through rate (CTR)
  • An indicator for missing average-position data

The target was binary:

  • 1 = June impressions declined compared with May
  • 0 = June impressions did not decline

One important part of the evaluation was the split strategy. I used a client-grouped train/test split, so clients in the test set were completely separate from clients used for training. This made the evaluation stricter and reduced the chance that the model was only learning client-specific patterns.

I compared three approaches:

  • A simple heuristic baseline
  • Logistic Regression
  • Random Forest

Results

Method Precision@20 Precision@50
Test-set base rate 0.728 0.728
Baseline 0.80 0.74
Logistic Regression 0.70 0.76
Random Forest 0.95 0.96

The Random Forest gave the strongest ranking performance. Out of the top 50 pages it ranked for review, 48 were observed to decline in the following month.

The test-set decline rate was already fairly high at about 72.8%, so I did not treat the raw precision numbers alone as enough evidence. The main point is that the Random Forest ranked declining pages much more effectively near the top of the queue than the baseline or Logistic Regression.

Content age was the strongest predictive feature in the final Random Forest, followed by CTR and average position. These values only describe how useful the features were to this model. They do not prove that any of these features directly cause search performance to rise or fall.

Ranked Recommendations

The final output is a ranked review queue rather than an automatic content-editing system. Each page receives a model score along with simple reason codes that help explain why it appears high in the ranking.

The main reason codes used were:

  • OLDER_CONTENT — the page is relatively old
  • LOW_CTR — the page receives impressions but captures relatively few clicks
  • WEAK_AVG_POSITION — the page tends to appear lower in search results
  • HIGH_VISIBILITY — the page already receives meaningful search exposure

Based on those signals, the review queue maps pages to actions such as:

  • Prioritize content and metadata review
  • Prioritize refresh review
  • Review title, snippet, and search-intent alignment
  • Review content depth and relevance
  • Monitor when the evidence is weaker

Limitations & Honest Framing

This project is observational. It looks for patterns in historical search data and does not prove that refreshing a page will improve rankings, clicks, or traffic.

The decline label is also only a proxy for refresh opportunity. A page can decline for reasons that have nothing to do with content quality, including seasonality, search-demand changes, competition, technical changes, or search-engine updates.

The grouped validation makes the evaluation more realistic, but it still does not guarantee the same performance on every future client or time period.

For these reasons, I would use the model to decide what to inspect first, not to automatically rewrite or remove content.
